## 1. 背景与目标
现有仓库以"产品化交付"为标准设计，模块拆分细且可扩展性强，但对于仅需快速演示的 PoC（Proof of Concept）来说：
* **代码量大**：约 10+ 个模块 / 2 万余行字符，学习与修改成本高。
* **依赖复杂**：多层抽象、日志系统、截图与重试机制等并非 PoC 必要。
* **启动门槛高**：新人拉仓库后，需要理解工厂模式、选择器管理器等概念。

因此计划将现有项目 **平行重构** 为一套极简版 PoC，实现"10 分钟上手、1 天完成演示"的目标，同时保留向完整产品路径回迁的可能性。

## 2. 范围与不在范围
| 范围内 | 说明 |
| ------ | ---- |
| ① 目录结构精简 | 删减不必要模块，保留 PoC 所需最小文件集合。 |
| ② 业务流程合并 | 把"抓取 → 合并 → 写 Excel"流程重写为脚本式或单文件函数。 |
| ③ 配置与依赖简化 | 仅保留 `config.yml` + `.env`；依赖控制在 selenium / playwright、pandas、openpyxl 等少量库。 |
| ④ 文档重写 | 提供新的 `README_PoC.md` 与简易使用说明。 |

| 不在范围（Out of Scope） | 说明 |
| ------------------------ | ---- |
| UI 测试、截图、重试 | PoC 阶段不实现。 |
| 平台扩展（>2 平台） | 留出接口但不实现。 |
| CI/CD 与 Docker 化 | 后续产品化阶段再处理。 |

## 3. 重构原则
1. **单一脚本优先**：能写在一个文件的不拆分，先保证可读性与易改性。
2. **最少依赖**：严格控制第三方库数量；能用标准库就不用外部库。
3. **快速失败**：用简单 `print` 提示代替复杂日志；异常直接抛出。
4. **可回迁**：保留与现有模块命名/配置格式的一致性，方便未来迁回。

## 4. 目标结构（完成后）
```
client-a-finance-automation/
├── poc/                       # 全新 PoC 目录
│   ├── config.yml             # 极简配置，只含 2 个平台
│   ├── credentials.env        # 账号密码
│   ├── main_poc.py            # **唯一** 主脚本
│   └── README_PoC.md          # 快速开始 & 使用说明
└── docs/
    └── PoC重构计划书.md
```

说明：
• 原有 `reusable_modules/`、`test_*.py`、日志与截图目录 **原封不动保留**，以便后续产品化继续使用。
• PoC 目录与完整框架 **互不干扰**，切换分支或脚本路径即可选择不同模式。

## 6. 实施步骤
1. **新建分支**：`feature/poc-refactor`
2. **搭建目录**：在 `poc/` 下创建所列文件；复制必要 util（如等待元素、保存 Excel）到脚本底部。
3. **实现功能**：参考前述 PoC 样例代码，逐步完成登录→抓取→合并→导出。
4. **最小验证**：在开发者本地跑通两平台示例。
5. **代码评审**：合并前仅关注可读性与功能正确性，不做过度抽象。
6. **文档同步**：`README_PoC.md` + 本计划书存档到 `docs/`。
7. **合并与标签**：合并到 `dev`，打 `v0.1-poc` Tag。

## 7. 质量保障
* **手动测试清单**
  - 正常账号登录抓取 → 生成 Excel
  - 错误密码 → 抛异常但脚本结束
  - 订单为空 → 生成仅表头的 Excel
* **代码检查**
  - flake8 / black 基本格式化
  - Python 3.10+ 兼容性

## 8. 风险与回滚
| 风险 | 影响 | 缓解 |
| ---- | ---- | ---- |
| PoC 代码误删产品化模块 | 产品功能受损 | 仅在 `poc/` 目录操作；不改旧代码 |
| Selenium 版本冲突 | 运行报错 | 使用 v4.18 固定版本；独立 `pyproject-poc.toml` |
| 演示平台 UI 变动 | 抓取失败 | 在 `config.yml` 中快速更新选择器 |

若 PoC 存在重大问题，可随时回滚分支或删除 `poc/` 目录，不影响原框架。
